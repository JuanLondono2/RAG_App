[3] ESTRATEGIA DE SEGMENTACION - ARBITRARIEDAD EN EL CHUNK POR PAGINAS
--------------------------------------------------------------------------------
El notebook segmenta los documentos en grupos de 20 páginas:
    f"{documento}_{documento_original}_parte_{pagina//20}"

  Problema: Este criterio es arbitrario y puede separar secciones
  temáticamente coherentes (por ej., un capítulo que empieza en la página 19
  y termina en la 25 queda dividido).

  Sugerencias:
  - Usar segmentación basada en estructura del documento (índice, títulos)
  - Aplicar modelos de detección de límites de tópicos (TextTiling, BERTopic)
  - Al menos documentar el fundamento del umbral de 20 páginas

--------------------------------------------------------------------------------
[4] ESTRATEGIA DE CHUNKING - BASADA EN PALABRAS VS. SEMANTICA
--------------------------------------------------------------------------------
El chunking actual es por ventana deslizante de 200 palabras con overlap de 50.

  Limitaciones observadas:
  - Una oración puede quedar cortada exactamente en el límite del chunk
  - Datos numéricos (ej. "7% del PIB") pueden separarse del contexto explicativo
  - El error de análisis reportado (mezcla de cifras) probablemente tiene origen
    en esta etapa, no solo en la generación

  Sugerencias de mejora:
  a) Chunking por oraciones (usando spaCy o NLTK sentence tokenizer):
       from nltk.tokenize import sent_tokenize
       sentences = sent_tokenize(text, language='spanish')
       # Agrupar oraciones hasta llegar al tamaño deseado

  b) Chunking con respeto de límites de párrafo:
       chunks = text.split('\n\n')  # Divide por párrafos

  c) Recursive Character Text Splitter (LangChain):
       from langchain.text_splitter import RecursiveCharacterTextSplitter
       splitter = RecursiveCharacterTextSplitter(
           chunk_size=1000, chunk_overlap=200,
           separators=["\n\n", "\n", ".", " "]
       )

[5] PERSISTENCIA DEL INDICE FAISS
--------------------------------------------------------------------------------
El índice FAISS se reconstruye en cada ejecución del notebook. Para un sistema
RAG real esto es ineficiente.

  Sugerencia - guardar y cargar el índice:
    import faiss, pickle

    # Guardar
    faiss.write_index(index, "faiss_index.bin")
    with open("chunks_metadata.pkl", "wb") as f:
        pickle.dump(chunks, f)

    # Cargar (en ejecuciones posteriores)
    index = faiss.read_index("faiss_index.bin")
    with open("chunks_metadata.pkl", "rb") as f:
        chunks = pickle.load(f)

  Esto reduce el tiempo de setup de ~3-5 minutos a <1 segundo.

[8] FORMATO DE METADATOS EN EMBEDDINGS
--------------------------------------------------------------------------------
El texto enviado al modelo de embeddings incluye metadatos:
    f"Documento: {chunk['documento']}. Página: {chunk['pagina']}. {chunk['texto']}"

  Observación: Los metadatos de navegación (documento, página) no aportan
  valor semántico y pueden "contaminar" el espacio de embeddings, perjudicando
  la similitud coseno.

  Sugerencia: Separar el texto del contexto de metadatos:
    - Embebido: solo el texto del chunk
    - Metadatos: almacenados aparte para citación

  Esto es la práctica estándar en frameworks como LlamaIndex y LangChain.

[9] EVALUACION - METRICA RECALL@K INSUFICIENTE PARA EVALUAR RAG COMPLETO
--------------------------------------------------------------------------------
La única métrica utilizada es Recall@5 sobre keywords esperadas.

  Limitaciones:
  - Recall@5 = 1.0 para los 5 casos puede indicar un conjunto de test demasiado
    fácil o keywords demasiado generales
  - No evalúa la calidad de la respuesta generada
  - No hay conjunto de test separado del proceso de diseño (data leakage leve)

  Métricas adicionales recomendadas:
  a) Precision@k: de los k chunks recuperados, ¿cuántos son realmente relevantes?
  b) MRR (Mean Reciprocal Rank): posición del primer chunk relevante
  c) Para la generación - ROUGE o BERTScore comparando contra respuestas ground truth
  d) Faithfulness: ¿la respuesta se puede sustentar en los chunks recuperados?
     (implementable con LLM-as-judge)

  Ejemplo mínimo de Precision@k:
    def precision_at_k(retrieved_chunks, relevant_keywords, k=5):
        hits = sum(
            any(kw in chunk['texto'].lower() for kw in relevant_keywords)
            for chunk in retrieved_chunks[:k]
        )
        return hits / k

[13] POSIBILIDAD DE USAR FRAMEWORKS ESPECIALIZADOS
--------------------------------------------------------------------------------
Para un proyecto de mayor escala o producción, se recomienda explorar:

  - LangChain (langchain.com): abstracción completa de pipelines RAG,
    múltiples loaders de documentos, text splitters, vector stores, etc.
  - LlamaIndex: especializado en RAG sobre documentos, soporta índices
    jerárquicos y query engines más sofisticados
  - Haystack (deepset.ai): pipeline RAG orientado a producción

  Para el contexto académico del taller, la implementación desde cero es
  válida y demostró los conceptos fundamentales correctamente.

[14] MODELO GENERATIVO - ALTERNATIVAS CONSIDERADAS
--------------------------------------------------------------------------------
Qwen2.5-0.5B-Instruct fue una buena elección por su tamaño reducido,
pero para mejorar la calidad de respuestas se pueden considerar:

  Modelos en español (mejores para este dominio):
  - BERTIN-GPT-J-6B: GPT-J fine-tuneado en español
  - IberLM: modelos de lenguaje en iberoamericano
  - Llama 3.2 1B/3B Instruct: mejor balance calidad/tamaño que Qwen 0.5B
  - Gemma 2 2B: alternativa moderna de Google, buen rendimiento en español

  Vía API (sin costo de cómputo local):
  - Groq API: llama3-8b-8192 gratuito con latencia muy baja
  - OpenAI API: gpt-4o-mini para mejor calidad en contextos limitados
  - Anthropic API: claude-haiku para respuestas más precisas
